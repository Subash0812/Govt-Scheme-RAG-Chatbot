1. WHAT THIS PROJECT IS
--------------------------------------------------------------------------------

SchemeSathi is an English-language RAG chatbot that helps people explore Indian
government welfare schemes. It is a portfolio/resume project, so code clarity,
visible evaluation numbers, and honest citations matter as much as features.

The corpus is 46 real scheme documents scraped from the MyScheme portal
(myscheme.gov.in). Each document describes one scheme: what it is, who is
eligible, what the benefits are, how to apply, and what documents are needed.

The hard problem this project is solving is RETRIEVAL, not generation. Users ask
two very different kinds of question:

  (a) NAMED   — "What documents do I need for the Annal Ambedkar Business
                Champions Scheme?"  (one specific scheme is named)
  (b) BROAD   — "I am a farmer, what financial help can I get?"
                (no scheme named; the system must DISCOVER which schemes apply)

Flat vector search over chunks handles (a) well and (b) badly, because a broad
question matches whichever chunk happens to use similar words, not the set of
schemes that actually serve that person. Most of the recent work has been about
fixing (b).

Answer generation is deliberately conservative: answers must come only from
retrieved context, must cite official source URLs, and must never claim a user
is definitely eligible. There is an offline extractive fallback when no
GEMINI_API_KEY is present.

4. THE PIPELINE, IN ORDER
--------------------------------------------------------------------------------

Every stage is idempotent and reads/writes plain files. To rebuild everything
from scratch on a new machine, run these in order from the repo root:

  Stage 1-2  Ingestion + cleaning
             (already done; raw_filtered/ and cleaned_v3/ are committed.
              Only rerun if you re-scrape.)
             python -m src.ingestion.processpdfsv3
             python -m src.ingestion.cleanerv3

  Stage 3    Metadata extraction — CALLS THE GEMINI API, costs quota, and is
             slow by design (4 s delay between requests, up to 6 retries with
             exponential backoff). It skips any scheme whose JSON already
             exists, so it is safe to rerun and resume.
             Requires GEMINI_API_KEY in .env.
             python -m src.metadata.extract_metadata
             NOTE: MODEL_NAME is hardcoded as "gemini-3.6-flash" in that file.
             Verify this is a real, available model before running — if the
             name is wrong every request will fail. rag.py separately defaults
             to "gemini-2.5-flash" via the GEMINI_MODEL env var.

  Stage 4    Chunking — local, fast, no API.
             python -m src.chunking.run_chunking
             Reads data/processed/cleaned_v3/*.txt + data/processed/metadata/*.json
             Writes data/processed/chunks/{recursive,fixed}/*.json

  Stage 5    Chunk index — downloads BAAI/bge-base-en-v1.5 on first run.
             python -m src.embeddings.build_faiss_index
             Reads data/processed/chunks/recursive/*.json
             Writes data/vector_store/bge_base_en_v1_5/{index.faiss,chunks.json,manifest.json}

  Stage 6    Scheme-card index — must run AFTER stage 5.
             python -m src.embeddings.build_scheme_card_index
             Writes scheme_index.faiss, scheme_cards.json, scheme_manifest.json

  Stage 7    Evaluation — read-only, writes reports.
             python -m src.embeddings.evaluate_router_retrieval

  Stage 8    The app (currently broken).
             streamlit run app.py

7. RETRIEVAL ARCHITECTURE
--------------------------------------------------------------------------------

Model: BAAI/bge-base-en-v1.5 (SentenceTransformer), 768 dimensions, run on CPU.
Vectors are L2-normalized and stored in faiss.IndexFlatIP, so inner product
equals cosine similarity. Queries are encoded with the BGE prefix
"Represent this sentence for searching relevant passages: " (retrieval_router.QUERY_PREFIX).
Documents/cards are encoded WITHOUT the prefix. This asymmetry is required by
BGE — do not "fix" it.

TWO INDICES:
  index.faiss        274 chunk vectors. Answers questions ABOUT a known scheme.
  scheme_index.faiss  46 card vectors. DISCOVERS which schemes fit a broad need.

SCHEME CARDS (src/embeddings/build_scheme_card_index.py)
  One card per scheme. card_text is what gets embedded:
    Scheme: <name>
    Abbreviation: / State or territory: / Ministry: / Department: /
    Scheme type: / Sponsorship: / Application mode:
    Beneficiary categories: <; separated>
    Summary: <up to 4 sentences, max 1400 chars>
  The Summary line is the recent fix. It is built by build_summary() from the
  scheme's "General"-section chunks, falling back to "Details" when General
  holds only scraped UI noise. clean_chunk_text() strips MyScheme navigation
  residue; sentences under 35 chars, UI-noise sentences, and duplicates are
  dropped. Config constants: SUMMARY_SECTION, SUMMARY_FALLBACK_SECTION,
  SUMMARY_SENTENCES=4, SUMMARY_MAX_CHARS=1400.
  Max card is 420 tokens — deliberately under BGE's 512-token window. Do not
  raise SUMMARY_MAX_CHARS much without checking token counts, or cards get
  silently truncated by the model and retrieval degrades.
  Metadata-only cards scored badly on broad queries; see section 8.

ROUTER (src/embeddings/retrieval_router.py, class SchemeRetrievalRouter)
  SchemeRetrievalRouter.from_local_store() is the constructor.
  retrieve(question, scheme_limit=3, chunks_per_scheme=3) -> RetrievalResult

  Route 1 "exact_scheme":
    scheme_matching.match_scheme() resolves a scheme name or abbreviation in the
    question (exact, else fuzzy at FUZZY_THRESHOLD=0.86 with an
    AMBIGUITY_MARGIN=0.04 guard). On a hit, chunk ranking is restricted to that
    one source_file. Precise, and immune to cross-scheme contamination.

  Route 2 "broad_scheme_discovery":
    No scheme named. Rank the 46 cards, take the top scheme_limit, then for each
    rank its own chunks with rank_source_chunks() and take chunks_per_scheme.

  RetrievalResult carries: route, exact_match, schemes (list[SchemeHit]),
  chunks_by_source (dict source_file -> list[ChunkHit]). ChunkHit includes
  rank_within_scheme, which is what revealed the "3 chunks is too shallow"
  problem.

9. FUTURE WORK, IN PRIORITY ORDER
--------------------------------------------------------------------------------

The order below is deliberate. The Streamlit app is DEFERRED to P7 by explicit
instruction: "leave that streamlit app that is not yet finalised, first we'll do
the development of the RAG system." Do not start at the app. Work P1 -> P6 first
and validate every change with the evaluation harnesses, not with the UI.

P1. APPLY THE MEASURED ROUTER SETTINGS. Do not ship the defaults.
    - Named/exact route: chunks_per_scheme=5, not 3. Evidence recall@5 goes
      50% -> 100%. Four gold chunks sit at within-scheme rank 4, one at rank 5.
    - Broad route: scheme_limit=5, not 3. P@1 and MRR are identical, and R@5
      rises 44.8% -> 57.3%. Several gold schemes sit at card rank 4-6.
    - Descriptive single-scheme questions: flat retrieval still wins (79% vs
      76% P@1). Keep a flat fallback path; do not route everything through
      cards.

P2. ROUTE GUARDRAILS. Exact-route precision is only 66.7%. Three known false
    positives, all in scheme_matching.match_scheme():
      - "goa-housing-2": question names Assam's "Aponar Apon Ghar" as a CONTRAST
        ("named differently from"). Router goes to the contrast scheme.
      - "agri-business-training-2": the phrase "agricultural extension service
        providers" fuzzy-matches the "Agricultural Extension" title; gold is
        Agri-Clinics.
      - "labour-board-death-gujarat-2": generic "accidental-death benefit"
        fuzzy-matches the Puducherry scheme; gold is Gujarat.
    Fix: refuse the exact route when the query contains multiple scheme titles,
    contrast/negation cues ("not", "instead", "named differently from"), or only
    a generic title. Ask for clarification when fuzzy candidates are within
    AMBIGUITY_MARGIN.

P3. HYBRID / LEXICAL CARD RETRIEVAL. The remaining broad-query failures are
    lexical, not semantic.
      - "economically weaker sections": aaby.txt contains that EXACT phrase in
        its beneficiary_category metadata, yet its card still ranks 22/46.
        Prose enrichment moved it 29 -> 22 and no further.
      - "low-income-student" (gold aaby, aavy): fails outright at every card
        rank (19 and 32). The supporting sentences exist in those documents —
        aaby has "scholarship to the children of the insured", aavy has "free
        education to poor children of construction workers" — but neither lands
        in the first four General-section sentences, and the query phrasing
        matches education-loan cards harder.
    Add BM25 or an exact-phrase boost over card_text, or take the semantic
    top-20 and rerank with a cross-encoder. This is now the top retrieval lever.

P4. CHUNK RERANKING. Top-1 evidence is only 40% even when recall@5 is 100% —
    the first chunk of a scheme is usually its intro, not the
    eligibility/benefits/documents section the question asks about. Chunk
    metadata already carries "section"; use it, or rerank within-scheme
    candidates with a cross-encoder.

P5. EXPAND THE BROAD TEST SET. 8 hand-labeled cases drove the card-enrichment
    decision, and several strategy deltas were exactly one case wide. Growing
    data/evaluation/broad_retrieval_cases.json to 25-30 questions would make the
    next round of tuning trustworthy. Gold lists are high-confidence, not
    exhaustive — that is a known labeling limitation.

P6. REPO HYGIENE.

10. CONVENTIONS AND GOTCHAS
--------------------------------------------------------------------------------

- Encoding. The corpus contains the rupee sign and Devanagari text. On Windows
  every command needed PYTHONIOENCODING=utf-8 to avoid a cp1252
  UnicodeEncodeError. On Linux this is unnecessary — UTF-8 is the default. If
  you see that error, something is still running under a Windows code page.

- Do not run stages out of order. build_scheme_card_index reads the chunk index
  artifacts; the evaluation harness reads both. If you rebuild chunks (stage 4)
  you MUST rerun stages 5, 6 and 7, or the indices silently disagree with the
  chunk files and every metric is wrong.

- first_nonempty() in build_scheme_card_index.py RAISES on inconsistent
  metadata. That is intentional: it caught real cases where one scheme's chunks
  disagreed about the state or ministry. If it fires, fix the metadata JSON in
  data/processed/metadata/ — do not weaken the check.

- The preprocessor (src/chunking/preprocessor.py) is doing real work on dirty
  scraped HTML: it strips MyScheme navigation chrome, splits inline section
  headings ("BenefitsUnder..." -> heading + body), removes a duplicated second
  copy of the document that MyScheme pages often contain, and normalizes lists.
  Chunk quality depends on it. If retrieval regresses after touching ingestion,
  look here first.

- Section headings are duplicated as a list in BOTH preprocessor.py and
  common.py, and the two lists are not identical (preprocessor also has
  "Negative List of Activities"). Keep them in sync or extract a shared constant.

- Chunking config: RecursiveCharacterTextSplitter, CHUNK_SIZE=500 tokens,
  CHUNK_OVERLAP=75, length measured with tiktoken cl100k_base. Non-"General"
  sections get a "Section: <name>" prefix injected into the chunk text.

- The 75-token overlap means adjacent chunks share sentences. Any dedupe or
  summarization logic over chunk text must account for that.

- Tests use a FakeModel returning 2-dim vectors, so they never load the real
  419 MB model. Keep it that way — the suite runs in ~10 ms.

- Nothing in this repo is deployed. There is no secrets management beyond the
  local .env. Never commit .env.
